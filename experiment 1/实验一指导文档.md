## 1. 实验目标

数据库把数据存在磁盘上，按 4 KB 一页切开。内存里划出一块固定大小的区域当缓存，叫 **缓冲池（buffer pool）**，里面每个格子叫一个 **帧（frame）**。上层只需要说"我要第 7 页"，缓冲池负责把数据端上来，哪怕它现在还在磁盘上。

P1 要你把这条链路自己实现出来，分三个部件：

```
              ┌──────────────────────────────────────────┐
   上层        │  BufferPoolManagerInstance               │
   (SQL 引擎)  │  ├─ page_table_ : page_id → frame_id     │
      │        │  │    （用你写的 ExtendibleHashTable）    │
      └───────▶│  ├─ replacer_   : 该淘汰哪个帧            │
               │  │    （用你写的 LRUKReplacer）           │
               │  ├─ free_list_  : 空闲帧                  │
               │  ├─ pages_      : 帧数组（Page 对象）     │
               │  └─ latch_      : 全局锁                  │
               └───────────────┬──────────────────────────┘
                               │ ReadPage / WritePage
                        ┌──────▼───────┐
                        │ DiskManager  │  ← 已经给你了，不用写
                        └──────────────┘
```

三个部件是**依赖关系**：哈希表负责"页在哪"，替换器负责"满了踢谁"，缓冲池把两者串起来。所以实现顺序建议：

**ExtendibleHashTable → LRUKReplacer → BufferPoolManagerInstance**

（缓冲池的构造函数里就 `new ExtendibleHashTable` 和 `new LRUKReplacer`，前两个不通，第三个没意义。）

### 你要改的 6 个文件

```

src/include/buffer/lru_k_replacer.h                  src/buffer/lru_k_replacer.cpp
src/include/buffer/buffer_pool_manager_instance.h    src/buffer/buffer_pool_manager_instance.cpp
```

## 3. 任务一：可扩展哈希表 ExtendibleHashTable

### 3.1 它解决什么问题

缓冲池需要一个 `page_id → frame_id` 的映射，而且**大小事先不知道**（数据库可能有很多页）。

- 普通哈希表：数组大小固定，扩容要整体 rehash，代价 O(n)
- 链式哈希：桶无限长，查找退化成链表扫描
- **可扩展哈希**：桶满了就"分裂"，每次只搬一个桶的数据，代价 O(桶大小)

而且要求：**不许用 `unordered_map` 等现成哈希表**，必须自己实现——因为这道题考的就是实现哈希结构。

### 3.2 两个关键概念

| 概念 | 含义 |
|---|---|
| **全局深度** `global_depth_` | 目录用键的**前 g 位**做索引，目录有 `2^g` 个槽 |
| **局部深度** `depth_` | 某个桶实际用到前 d 位，`d ≤ g` |

当 `d < g` 时，说明**多个目录槽指向同一个桶**（这些槽共享前缀），这些指针叫"兄弟指针"。

索引计算（**已经给你写好了**）：

```cpp
// extendible_hash_table.cpp:28
int mask = (1 << global_depth_) - 1;
return std::hash<K>()(key) & mask;
```

也就是说取哈希值的**低 g 位**。

### 3.3 已经给好的部分

这些不用你写，也别改坏：

| 已实现 | 说明 |
|---|---|
| `IndexOf(key)` | 上面那段，取低 g 位 |
| `GetGlobalDepth()` / `GetLocalDepth(i)` / `GetNumBuckets()` | 已经加锁，调用对应的 `*Internal()` |
| `Bucket` 的构造 `Bucket(size, depth)` | 存放 `list_`、`size_`、`depth_` |
| 文件末尾的**显式实例化** | 见 3.7，很重要 |

### 3.4 你要实现的 6 个函数

```cpp
// 表这一层
auto Find(const K &key, V &value) -> bool;
void Insert(const K &key, const V &value);
auto Remove(const K &key) -> bool;
auto GetGlobalDepthInternal() const -> int;
auto GetLocalDepthInternal(int dir_index) const -> int;
auto GetNumBucketsInternal() const -> int;

// 桶这一层（嵌套类 Bucket）
auto Find(const K &key, V &value) -> bool;
auto Insert(const K &key, const V &value) -> bool;
auto Remove(const K &key) -> bool;
```

**语义**（照着写就不会错）：

- `Bucket::Insert`：键已存在 → **覆盖**值返回 true；桶未满 → 追加返回 true；桶满 → 返回 **false**（不是抛异常）
- `Bucket::Find`：找到就把值**写进 `value` 参数**并返回 true
- `Bucket::Remove`：找到就删并返回 true，否则 false
- `Table::Insert`：**返回 void**，失败不报错——它是靠循环重试保证成功的
- `Table::Find` / `Remove`：先算 `IndexOf`，再去对应桶里操作

### 3.5 `Insert` 的完整流程（最容易写错的地方）

教程反复强调一句话：**"检测桶是否溢出，并在插入之前执行拆分"**。也就是**先拆后插**，不是插完发现满了再拆。

```
Insert(key, value):
    bucket = dir_[IndexOf(key)]
    if bucket 已满 且 key 不在桶里:
        while bucket 仍然满:
            如果 bucket->depth == global_depth:
                global_depth += 1
                目录翻倍：dir_.resize(2^g)，把前一半的指针复制到后一半
            把原来指向这个 bucket 的所有兄弟槽都换成两个新桶
            bucket->depth += 1
            新建一个桶，depth 与旧桶相同
            把旧桶里的所有 <k,v> 按新的 depth 重新分到两个桶（RedistributeBucket）
            重新计算 key 应该落在哪个桶，把 bucket 指向它
    bucket->Insert(key, value)
```

几个必须注意的点：

1. **目录翻倍要复制前半段**：`dir_[i + old_size] = dir_[i]`，这样每个桶自动多出一个兄弟指针。
2. **兄弟指针可能不止两个**：如果 `d < g`，可能有 `2^(g-d)` 个槽指向同一个桶，拆分时要**全部**改掉。
3. **拆完不等于能插**：所有键可能又被分到同一个桶里（哈希低位相同），所以要 **`while` 循环**反复拆，直到桶不满。
4. **`num_buckets_` 每次新建桶要 +1**，`GetNumBuckets` 才正确。

拆分示意（`d == g` 时目录翻倍）：

```
分裂前 g=2, d=2             分裂后 g=3, d=3
目录: [0]→B0                目录: [0]→B0
      [1]→B1                       [1]→B1
      [2]→B2  ← 满                 [2]→B2
      [3]→B3                       [3]→B2'
                                   [4]→B0   ← 复制
                                   [5]→B1
                                   [6]→B2
                                   [7]→B3
```

### 3.6 构造函数的坑（第一个必踩）

骨架的构造函数**只设置了 `bucket_size_`**：

```cpp
ExtendibleHashTable(size_t bucket_size) : bucket_size_(bucket_size) {}
```

此时 `dir_` 是**空的**，`global_depth_ = 0`，`num_buckets_ = 1`。

**后果**：`GetLocalDepthInternal(0)` 里访问 `dir_[0]` 直接越界 → **段错误**。
这就是你第一次跑 `extendible_hash_table_test` 看到的那个 `AddressSanitizer: SEGV`。

**修法**：构造函数里创建初始桶并放进目录：

```cpp
dir_.push_back(std::make_shared<Bucket>(bucket_size_, 0));   // 深度 0
```

一条语句，但漏了它整个测试文件一个用例都跑不了。

### 3.7 模板代码写在 .cpp 里，为什么能编译？

因为文件末尾有**显式实例化**：

```cpp
template class ExtendibleHashTable<page_id_t, Page *>;

template class ExtendibleHashTable<int, std::string>;   // 测试用的就是这个
```

**影响**：如果你新增的是**成员函数**，写在 .cpp 里没问题（会随类一起实例化）。但如果你新增**独立的模板辅助类/函数**，需要自己补一行 `template class ...;`，否则链接时会报 undefined reference。

### 3.8 并发

所有公开函数开头加 `std::scoped_lock<std::mutex> lock(latch_);`（`Get*` 已经加了，别重复加）。

注意 `latch_` 是 `mutable` 的，所以 const 函数里也能锁。

**不要**在持锁时调用另一个也会加锁的函数——`std::mutex` 不可重入，会直接死锁。所以骨架才把 `GetGlobalDepth`（加锁）和 `GetGlobalDepthInternal`（不加锁）分开：**内部互相调用一律用 `*Internal` 版本**。

## 4. 任务二：LRU-K 替换器 LRUKReplacer

### 4.1 算法定义

**后退 k-距离**（backward k-distance）= 当前时间戳 − 第 k 次先前访问的时间戳。

淘汰规则：

1. 访问次数 **≥ k** 的帧：淘汰后退 k-距离**最大**的（也就是第 k 次访问距今最远的）
2. 访问次数 **< k** 的帧：其后退 k-距离视为 **+∞**，这类帧**优先被淘汰**
3. 多个都是 +∞ 时：按传统 LRU 处理，淘汰**最早被访问**的（第一个时间戳最旧）
4. 帧标记为 `evictable = false` 时，**完全不参与**上述选择

### 4.2 用两个列表来理解

把帧分成两份：

| 列表 | 存放 | 排序依据 |
|---|---|---|
| 历史列表 | 访问次数 `< k` 的帧 | 第一次访问时间（越旧越先淘汰） |
| 缓存列表 | 访问次数 `≥ k` 的帧 | **第 k 次访问时间**（K-time，越旧越先淘汰） |

一个帧访问满 k 次时，从历史列表"晋升"到缓存列表。

`LRU-2 算法的例子.pdf` 里有完整推演，值得跟着走一遍。关键洞察是：
**LRU-K 保护的是"新晋热点"，而不是"最近被访问过的"**——一个老帧即使刚被访问，只要它的 K-time 很旧，仍会被淘汰。这正是它抗顺序扫描的原因。

### 4.3 类里给了什么、缺什么

```cpp
private:
  size_t current_timestamp_{0};   // 逻辑时钟，每次 RecordAccess +1
  size_t curr_size_{0};           // 可驱逐帧的数量
  size_t replacer_size_;          // 帧总数上限
  size_t k_;                      // K
  std::mutex latch_;
```

**注意：没有现成的容器！** 你得自己加，例如：

```cpp
std::unordered_map<frame_id_t, LRUKNode> node_store_;   // 每个帧的访问历史
```

`LRUKNode` 也只有一个空类，字段要你自己定义（至少要有：最近 k 次访问的时间戳列表、是否可驱逐）。

### 4.4 五个函数的语义细节

**`Evict(frame_id_t *frame_id) -> bool`**

- 通过**指针出参**返回被淘汰的帧号（不是返回值）
- 没有可淘汰的帧 → 返回 `false`，**不要改动 `*frame_id`**
- 成功 → 从容器里**删除**该帧的记录，`curr_size_--`，返回 `true`

**`RecordAccess(frame_id_t frame_id)`**

- `current_timestamp_++`，把新时间戳追加到该帧的历史里
- 历史**只保留最近 k 条**（超出就丢弃最旧的）
- 帧号越界（`>= replacer_size_`）→ 抛异常或 `BUSTUB_ASSERT`（教程允许两种）
- **不改变 `curr_size_`**：访问本身不代表可驱逐

**`SetEvictable(frame_id_t frame_id, bool set_evictable)`**

这是最容易写错的一个，记住三条：

1. **只在状态真的变化时才改 `curr_size_`**
   - `false → true`：`curr_size_++`
   - `true → false`：`curr_size_--`
   - 本来就是 true 又设 true：**什么都不做**
2. 帧不存在 → 直接返回，不要抛异常（教程原文："For other scenarios, this function should terminate without modifying anything"）
3. 帧号越界 → 抛异常

**`Remove(frame_id_t frame_id)`**

- 删除**指定**帧（和"挑一个淘汰"的 `Evict` 不同）
- 该帧**不可驱逐** → 抛异常（这是调用方 bug）
- 帧不存在 → 直接返回
- 成功 → `curr_size_--`

**`Size()`** → 返回 `curr_size_`，即**可驱逐**帧数，不是登记总数。

### 4.5 复杂度怎么选

| 方案 | Evict | 说明 |
|---|---|---|
| 每次线性扫 `node_store_` | O(n) | 最简单，n = 缓冲池大小（通常几十到几千），**测试能过** |
| 额外维护两个有序结构 | O(1) 或 O(log n) | 更快，但要处理大量边界 |

建议：**先写 O(n) 版本把 4 个用例跑通**，再考虑优化。课程测试不卡复杂度，卡的是正确性。

### 4.6 并发

所有公开函数加 `std::scoped_lock<std::mutex> lock(latch_);`。`ConcurrencyTest` 会多线程狂调这五个函数。

### 4.7 验收：4 个用例

| 用例 | 考点 |
|---|---|
| `SampleTest` | 基础流程：`Size` 只数可驱逐的、淘汰顺序 |
| `Evict` | 后退 k-距离的比较、+∞ 优先级、并列时取最旧 |
| `Size` | 各种 `SetEvictable` 组合后的计数 |
| `ConcurrencyTest` | 多线程安全 |

### 4.8 常见错误

| 现象 | 原因 |
|---|---|
| `Size()` 对不上 | `SetEvictable` 重复设置时也改了计数 |
| 淘汰顺序不对 | 把"最近一次访问"当成排序依据（那是 LRU，不是 LRU-K） |
| 淘汰了 pinned 帧 | `Evict` 没过滤 `is_evictable == false` |
| 死锁 | 内部函数互相调用，都加了锁 |
| 越界没抛异常 | 少了 frame_id 合法性检查 |

## 5. 任务三：缓冲池管理器 BufferPoolManagerInstance

### 5.1 成员变量职责

| 成员 | 作用 |
|---|---|

`Page` 对象的三个关键字段：`page_id_`（`INVALID_PAGE_ID` 表示空）、`pin_count_`、`is_dirty_`。

### 5.2 第一件事：删掉构造函数里的 throw

### 5.3 六个函数

**`NewPgImp(page_id_t *page_id) -> Page *`**

```
1. 取一个可用帧：
   有 free_list → 从前端弹一个
   否则 → replacer_->Evict(&fid)；Evict 失败（全 pinned）→ 返回 nullptr
2. 若该帧里有旧页：
   - 旧页 is_dirty → disk_manager_->WritePage(旧页号, 数据)
   - page_table_->Remove(旧页号)
   - 清空帧（ResetMemory、page_id_ = INVALID_PAGE_ID、is_dirty_ = false）
3. pid = AllocatePage()；*page_id = pid
4. 把 pid ↔ fid 写进 page_table_
5. replacer_->RecordAccess(fid)；replacer_->SetEvictable(fid, false)
6. pages_[fid].pin_count_ = 1；pages_[fid].page_id_ = pid
7. 返回 &pages_[fid]
```

**`FetchPgImp(page_id_t page_id) -> Page *`**

```
1. page_table_ 里查得到 → 命中：
   pin_count_++；replacer_->RecordAccess(fid)；SetEvictable(fid,false)；返回该帧
2. 没命中 → 拿帧（同 NewPgImp 的第 1、2 步）
3. 通过 disk_manager_->ReadPage(page_id, 帧数据) 读盘
4. 写入 page_table_，pin_count_ = 1，RecordAccess + SetEvictable(false)
5. 返回帧
```

**`UnpinPgImp(page_id, is_dirty) -> bool`**

```
1. page_table_ 里没有 → 返回 false
2. 只有当 is_dirty == true 时，才把 is_dirty_ 置 true
   （已经 dirty 的不会被改回 false —— 教程明确强调）
3. pin_count_ <= 0 → 返回 false（说明调用方 unpin 多了）
4. pin_count_-- 
5. 减到 0 → replacer_->SetEvictable(fid, true)
6. 返回 true
```

**`FlushPgImp(page_id) -> bool`** — 把该页写回磁盘，**然后把 `is_dirty_` 置 false**。页不在缓冲池里返回 false。

**`FlushAllPgsImp()`** — 遍历所有有效帧，写回并清 dirty。

**`DeletePgImp(page_id) -> bool`**

```
1. page_table_ 里没有 → 返回 true（本来就不在）
2. pin_count_ > 0 → 返回 false（还有人在用，不能删）
3. 若 dirty 先写回（也可以选择不写，但测试要求一致）
4. page_table_->Remove；replacer_->Remove(fid)；重置帧；fid 放回 free_list_
5. DeallocatePage(page_id)（目前是空函数，调用一下即可）
```

### 5.4 五条不变量（写完自我检查）

任何时候都应成立：

1. **`page_table_` 里有某页 ⟺ 某帧的 `page_id_` 等于它**
2. **`pin_count_ > 0` 的帧，`replacer_` 里一定是不可驱逐**
3. **`pin_count_ == 0` 的帧，`replacer_` 里一定是可驱逐**
4. **`free_list_` 里的帧，`page_id_ == INVALID_PAGE_ID`，且不在 `page_table_` 里**
5. **同一个 `page_id` 不会同时出现在两个帧里**

调试时把这五条写成断言，能挡住绝大部分 bug。

### 5.5 边界情况

| 情况 | 正确行为 |
|---|---|
| 池满且所有帧都被 pin | `NewPgImp` / `FetchPgImp` 返回 `nullptr`，`*page_id` 不要改 |
| `Fetch` 一个从没存在过的 page_id | 正常读盘（DiskManager 会给全 0 页），不要返回 null |
| `Unpin` 一个 pin_count 为 0 的页 | 返回 `false`，不要减成 -1 |
| `Delete` 一个 pinned 页 | 返回 `false` |
| `Flush` 一个不在池里的页 | 返回 `false` |
| 驱逐到 dirty 页 | 必须先 `WritePage` 再复用帧 |

### 5.6 并发

一个 `std::mutex latch_` 把六个函数全包住就能过 `ConcurrencyTest`（粗粒度锁，性能不重要，正确性重要）。

注意：`AllocatePage()` 用了 `std::atomic`，可以在锁外调用，但放在锁里也不会错。

**不要在持锁时调用会再次加锁的函数**——`page_table_` 和 `replacer_` 内部都有自己的锁，这没问题（不同的锁），但不能让 `NewPgImp` 再去调 `FetchPgImp`。

### 6.1 看 ASan 报告

Debug 构建自带 AddressSanitizer，出错会打印**文件名:行号 + 调用栈**：

```
ERROR: AddressSanitizer: heap-use-after-free on address 0x...
    #0 0x... in bustub::LRUKReplacer::Evict(...) src/buffer/lru_k_replacer.cpp:31
```

看 `#0` 那一行就够了，那通常是问题源头。

三类常见报告：

| 关键字 | 含义 |
|---|---|
| `SEGV on unknown address 0x000000000000` | 空指针解引用（最常见：忘了初始化、没判空） |
| `heap-use-after-free` | 用了已经释放的对象（`shared_ptr` 没管好） |
| `SUMMARY: ... N byte(s) leaked` | 内存泄漏，`new` 了没 `delete` |

### 6.4 测试超时 / 卡住

`ConcurrencyTest` 卡住不动 = **死锁**，九成是：

- 同一个 `std::mutex` 被同一线程锁了两次（可重入问题）
- 加锁顺序不一致（A 先锁 latch_ 再锁 table_，B 反过来）

`std::scoped_lock` 出作用域自动解锁，**不要在持锁时 `return` 前忘了**——用 RAII 就不会有这个问题。

### 6.5 一段万能排查法

在可疑函数入口打印状态：

```cpp
std::cerr << "Fetch pid=" << page_id << " pin=" << pin_count << " size=" << replacer_->Size() << "\n";
```

`HardTest` 挂掉时，把这几行加上，对比 `pin_count` 和 `Size()` 的变化，能很快定位是哪一步没同步。

## 附录：为什么不用普通 LRU 或 CLOCK

`CLOCK 时钟置换算法及其与 LRU 的关系.pdf` 里有个很好的反例：

容量 3 的缓冲池，访问序列 `A B C A D`，按 CLOCK 规则（引用位为 1 就清零跳过），
淘汰 D 时会绕一圈把 A、B、C 的引用位全清零，然后回到 A 把 **A** 淘汰——尽管 A 刚刚被访问过。
而 LRU 会淘汰 B。

结论：**CLOCK 近似的是 LRU 的"决策目标"，不保证复现 LRU 的结果**。它用 1 bit 换掉了精确的时间戳。

那 LRU-K 又强在哪？它记录最近 K 次访问，能区分"只被扫描过一次的页"和"反复被访问的页"：

- 顺序扫描（每个页只读一次）→ 全部滞留在历史列表，**永远进不了缓存列表**，冲不掉真热点
- 真热点 → 访问满 K 次后进入缓存列表，按 K-time 排序，获得保护

这就是为什么 `LRU-2 算法的例子.pdf` 里，被访问了两次的 A 仍然被淘汰，而 C、D 活到最后——
A 的 K-time 太旧，说明它只是"短暂的热点"。
