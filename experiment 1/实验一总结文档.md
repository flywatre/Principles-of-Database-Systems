## 一、实验概述

### 1.1 实验目标

数据库把数据以 4 KB 为单位存放在磁盘上，而内存中只能缓存其中一部分。**缓冲池管理器**负责在两者之间搬运数据，向上层提供"给我第 N 页"的接口，向上对磁盘提供读写请求，并在缓存满时按某种策略淘汰页面。

本实验要求实现缓冲池及其两个内部组件，共三个部分：

| 编号 | 组件 | 作用 |
|---|---|---|
| 1 | `ExtendibleHashTable` | 可扩展哈希表，维护 `page_id → frame_id` 的映射 |
| 2 | `LRUKReplacer` | LRU-K 页面置换算法，决定"缓存满了淘汰谁" |
| 3 | `BufferPoolManagerInstance` | 缓冲池本体，串起页表、替换器和磁盘 |

### 1.2 验收标准

三个测试文件共 **29 个用例**：

| 测试 | 用例数 | 覆盖内容 |
|---|---:|---|
| `extendible_hash_table_test` | 12 | 插入、查找、删除、桶分裂、目录翻倍、并发 |
| `lru_k_replacer_test` | 4 | 淘汰顺序、大小统计、并发 |
| `buffer_pool_manager_instance_test` | 13 | 页的创建/获取/释放/刷盘/删除、脏页、并发、压力测试 |

### 1.3 硬性约束

- 不可使用内置哈希表（如 `unordered_map`）实现可扩展哈希表
- 只允许修改指定的 6 个文件
- 所有数据结构必须线程安全（`std::mutex`）
- 遵循 Google C++ 风格，函数必须使用尾置返回类型
- **零内存泄漏**

实验最初计划在 VMware 虚拟机中完成，但原虚拟机是 **Ubuntu 16.04.7 i686（32 位）+ gcc 5.4**，存在三重硬性不兼容：

## 四、详细设计与实现

### 4.1 ExtendibleHashTable（可扩展哈希表）

#### 4.1.1 数据结构

可扩展哈希表由**目录（directory）**和**桶（bucket）**组成：

- **目录**：一个指针数组，长度 `2^global_depth`，每个槽指向一个桶
- **桶**：定长链表，存放 `<K, V>` 键值对，容量为 `bucket_size`
- **全局深度 g**：目录索引用键哈希值的低 g 位
- **局部深度 d**：某个桶实际使用低 d 位，`d ≤ g`

当 `d < g` 时，**多个目录槽指向同一个桶**（这些槽共享低 d 位），称这些指针为兄弟指针。

索引计算沿用框架提供的实现：

```cpp
int mask = (1 << global_depth_) - 1;
return std::hash<K>()(key) & mask;
```

#### 4.1.2 构造函数的关键修正

框架给出的构造函数只初始化了 `bucket_size_`：

```cpp
ExtendibleHashTable(size_t bucket_size) : bucket_size_(bucket_size) {}
```

此时 `dir_` 为空、`global_depth_ = 0`，而 `GetLocalDepthInternal(0)` 会访问 `dir_[0]`，**立即越界导致段错误**。这是初始状态下该测试文件一个用例都无法执行的根本原因。

修正方案：构造时创建唯一的初始桶。

```cpp
dir_.push_back(std::make_shared<Bucket>(bucket_size_, 0));
```

#### 4.1.3 插入算法

题目明确要求**"检测桶是否溢出，并在插入之前执行拆分"**，即先拆后插。实现采用循环重试：

```
Insert(key, value):
  lock
  loop:
    index  = IndexOf(key)
    bucket = dir_[index]

    if 桶中已存在 key:        # 覆盖，不算溢出
        bucket->Insert(key, value); return

    if 桶未满:
        bucket->Insert(key, value); return

    # 桶已满，需要拆分
    if bucket->depth == global_depth:
        global_depth += 1
        目录翻倍：dir_.resize(2 * size)，dir_[i + size] = dir_[i]

    old_depth = bucket->depth
    bucket->depth += 1
    new_bucket = 新桶（depth 与 bucket 相同）

    # 把原本指向旧桶的兄弟指针按新的区分位分成两半
    split_bit = 1 << old_depth
    for i in 0..|dir_|:
        if dir_[i] == bucket and (i & split_bit) != 0:
            dir_[i] = new_bucket

    num_buckets += 1
    RedistributeBucket(bucket)   # 旧桶里的键按新深度重新分配

    # 回到循环开头，可能还需继续拆分
```

**为什么必须用循环而不是单次 `if`**：拆分后旧桶中的键仍可能全部落到同一个桶（哈希低位相同），此时该桶依旧满载，必须继续拆分。用 `while` 保证最终一定能插入。

#### 4.1.4 拆分时目录翻倍的判定

关键判定是 `bucket->depth == global_depth`：

- **相等**：只有一个目录槽指向该桶，翻倍后才有第二个槽可用，必须先扩容目录
- **不相等**：已有多个兄弟指针，只重新分配它们即可，无需扩容

#### 4.1.5 键的重新分配

拆分后，旧桶中所有键需要用**新的全局深度**重新计算目录索引：

```cpp
auto items = std::move(bucket->GetItems());
bucket->GetItems().clear();
for (auto &kv : items) {
  dir_[IndexOf(kv.first)]->Insert(kv.first, kv.second);
}
```

由于桶中原有键的数量恰好等于容量，分到两个桶后各自不会超过容量，因此不会溢出。

#### 4.1.6 并发设计

采用一把粗粒度互斥锁 `latch_`：

- 所有公开接口（`Find` / `Insert` / `Remove` / `Get*`）进入时加锁
- 内部互相调用一律使用**不加锁的 `*Internal` 版本**，避免 `std::mutex` 不可重入导致的自我死锁

框架已将 `GetGlobalDepth` 等拆分为"加锁外壳 + 无锁内核"两层，本实现沿用该设计。

#### 4.1.7 复杂度

| 操作 | 平均 | 最坏 |
|---|---|---|
| Find / Insert / Remove | O(1) | O(n)（所有键集中在同一桶） |
| 单次拆分 | O(bucket_size) | — |

伸不需要整体 rehash，这是可扩展哈希相对普通哈希表的核心优势。

### 4.2 LRUKReplacer（LRU-K 替换器）

#### 4.2.1 算法定义

**后退 k-距离** = 当前时间戳 − 第 k 次先前访问的时间戳。淘汰规则分三层：

| 优先级 | 候选集合 | 选择依据 |
|---|---|---|
| 最高 | 访问次数 < k 的帧 | 后退 k-距离视为 **+∞** |
| 次高 | 多个 +∞ 之间 | **第一次访问时间最早**的（传统 LRU 语义） |
| 一般 | 访问次数 ≥ k 的帧 | 后退 k-距离**最大**的 |

此外，`evictable == false` 的帧完全不参与选择。

#### 4.2.2 数据结构

框架只提供了 `current_timestamp_` / `curr_size_` / `replacer_size_` / `k_` / `latch_`，**没有给定存取容器**，需要自行设计：

```cpp
class LRUKNode {
 public:
  std::list<size_t> history_;   // 最近 k 次访问的时间戳，旧在前
  bool is_evictable_{false};
};

std::unordered_map<frame_id_t, LRUKNode> node_store_;
```

用 `std::list` 而非 `deque` 是因为需要频繁从队首删除（历史超过 k 条时）。

#### 4.2.3 淘汰选择

单次遍历所有节点，边遍历边比较，无需额外排序：

```cpp
for (每个可驱逐帧) {
  is_inf   = (history.size() < k)
  earliest = history.front()
  distance = is_inf ? 0 : current_timestamp - history[倒数第 k 个]

  若 (尚无候选)                           → 选它
  否则若 (is_inf != 已选.is_inf)          → is_inf 者优先
  否则若 (都是 inf)                       → earliest 更小者优先
  否则                                    → distance 更大者优先
}
```

淘汰后从 `node_store_` 中删除该帧并 `curr_size_--`，通过出参 `frame_id` 返回帧号。

#### 4.2.4 各函数的语义细节

| 函数 | 关键点 |
|---|---|
| `Evict(&fid)` | 指针出参；无可淘汰帧返回 `false` 且**不改动** `*fid` |
| `RecordAccess(fid)` | 时间戳 +1 后追加，历史超过 k 条从队首丢弃；**不改变** `curr_size_` |
| `SetEvictable(fid, b)` | **幂等**：状态未变化时不得改动计数；帧不存在时直接返回 |
| `Remove(fid)` | 删除**指定**帧；对不可驱逐帧调用需抛异常；帧不存在直接返回 |
| `Size()` | 返回**可驱逐**帧数，不是登记总数 |

`SetEvictable` 的幂等性是最易出错处：若不加判断地对 `curr_size_` 加减，重复设置同一状态会导致计数漂移。

#### 4.2.5 复杂度权衡

当前 `Evict` 为 **O(n)** 线性扫描（n = 帧数）。理论上可以维护两个有序链表（历史列表 / 缓存列表）实现 O(1) 淘汰，但需要处理大量边界情况（帧晋升、删除、并列时间戳）。

本实验测试规模有限，线性扫描已足够；作为工程取舍，优先保证正确性。改进方向见第八节。

#### 4.2.6 为什么不用普通 LRU 或 CLOCK

- **普通 LRU** 只记录最近一次访问，无法区分"被扫描过一次的冷页"和"反复访问的热页"。全表顺序扫描会把真热点全部挤出缓存（顺序扫描污染）。
- **CLOCK** 用 1 bit 引用位近似 LRU，开销低，但**不保证复现 LRU 的决策**。存在这样的反例：容量 3、访问序列 `A B C A D`，CLOCK 会淘汰刚被访问过的 A，而 LRU 会淘汰 B。
- **LRU-K** 通过保留最近 K 次访问时间戳，使"访问不足 K 次的页"优先出局，从而**天然抵抗顺序扫描**：只读一次的页永远停留在历史列表，进不了缓存列表。

### 4.3 BufferPoolManagerInstance（缓冲池管理器）

#### 4.3.1 成员变量职责

| 成员 | 职责 |
|---|---|
| `pages_` | `Page` 数组，长度 `pool_size`，每个元素是一个帧 |
| `page_table_` | 可扩展哈希表，维护 `page_id → frame_id` |
| `replacer_` | LRU-K 替换器 |
| `free_list_` | 空闲帧号链表，构造时填满 |
| `next_page_id_` | 下一个分配的页号（`std::atomic`） |
| `latch_` | 保护上述所有共享结构 |

`Page` 对象通过 `friend` 声明允许缓冲池直接访问 `page_id_`、`pin_count_`、`is_dirty_`。

#### 4.3.2 提取公共逻辑：AcquireFrame

`NewPgImp` 与 `FetchPgImp` 都需要"取一个可用帧"，因此提取为私有辅助函数（需在头文件声明）：

```
AcquireFrame(&fid):
  1. free_list_ 非空 → 弹出一个，成功
  2. 否则 replacer_->Evict(&victim)
       失败（所有帧都被 pin）→ 返回 false
  3. 回收 victim 帧：
       旧页 dirty → WritePage 写回磁盘
       从 page_table_ 中移除旧页号
       ResetMemory、page_id_ = INVALID_PAGE_ID、is_dirty_ = false、pin_count_ = 0
  返回 true
```

这个函数把"空闲帧优先、无空闲则驱逐、驱逐前写回脏页"三条逻辑集中在一处，避免两个调用点各写一遍导致行为不一致。

#### 4.3.3 六个操作

**`NewPgImp(&page_id)`**

```
AcquireFrame 失败 → 返回 nullptr
pid = AllocatePage()
设置帧：page_id_ = pid，pin_count_ = 1，is_dirty_ = false
page_table_->Insert(pid, fid)
RecordAccess(fid)；SetEvictable(fid, false)
*page_id = pid；返回帧指针
```

**`FetchPgImp(page_id)`**

```
page_table_ 命中 → pin_count_++，RecordAccess，SetEvictable(false)，返回
未命中 → AcquireFrame → ReadPage 读盘 → 登记页表 → pin_count_ = 1 → 返回
```

**`UnpinPgImp(page_id, is_dirty)`**

```
页不在页表中 → false
pin_count_ <= 0 → false（调用方 unpin 过多）
is_dirty 为真时才置脏（已是脏的不会被改回干净）
pin_count_--；减到 0 → SetEvictable(fid, true)
```

**`FlushPgImp(page_id)`**：写回并清除脏标记；页不在池中返回 `false`。

**`FlushAllPgsImp()`**：遍历所有有效帧写回并清脏。

**`DeletePgImp(page_id)`**

```
页不在页表中 → true（视为已删除）
pin_count_ > 0 → false（仍被使用，不能删）
脏页先写回
从页表移除、从 replacer 移除、重置帧、帧号放回 free_list_
```

#### 4.3.4 五条不变量

实现过程中用以下不变量自检，任何一条被破坏都会导致 `HardTest` 失败：

1. `page_table_` 中存在某页 ⟺ 某帧的 `page_id_` 等于它
2. `pin_count_ > 0` 的帧在 replacer 中**不可驱逐**
3. `pin_count_ == 0` 的帧在 replacer 中**可驱逐**
4. `free_list_` 中的帧满足 `page_id_ == INVALID_PAGE_ID` 且不在页表中
5. 同一个 `page_id` 不会同时存在于两个帧

#### 4.3.5 并发设计

采用**一把全局互斥锁**保护六个操作。这是粗粒度设计，并发度不高，但正确性容易保证，足以通过 `ConcurrencyTest`。

需要注意的是，基类 `BufferPoolManager` 中的 `FetchPage` / `NewPage` 等包装函数**不加锁**，锁必须由 `*Imp` 实现自行获取——这一点若判断错误会导致数据竞争或死锁。

## 六、遇到的问题与解决

本节记录调试过程中实际遇到的问题，按"现象 → 根因 → 解决"组织。

### 问题 1：哈希表测试一开始就段错误

- **现象**：`extendible_hash_table_test` 首个用例 `SEGV on unknown address 0x000000000000`，一个用例都跑不完
- **根因**：构造函数只设置了 `bucket_size_`，`dir_` 为空 vector；`GetLocalDepthInternal(0)` 访问 `dir_[0]` 越界
- **解决**：构造时创建初始桶 `dir_.push_back(make_shared<Bucket>(bucket_size_, 0))`
- **收获**：ASan 的符号化调用栈能直接指出越界所在的文件和行号（需安装 `llvm-symbolizer`，否则只有裸地址）

### 问题 2：缓冲池测试全部抛出 `NotImplementedException`

- **现象**：13 个用例全部在构造 `BufferPoolManagerInstance` 时抛异常，看不到任何断言失败
- **根因**：框架在构造函数末尾故意留了一行 `throw NotImplementedException(...)`，防止学生忘记实现就提交
- **解决**：删除该行
- **收获**：这类"编译通过但一运行就抛"的现象，优先检查构造函数和 `UNIMPLEMENTED` 宏

### 问题 3：测试随机崩溃、无任何输出

- **现象**：`orset_test`、`robin_hood_hash_set_test` 在构建阶段发现用例时崩溃，重跑有时又正常
- **根因**：WSL 内核 `vm.mmap_rnd_bits = 32`，而 AddressSanitizer 的 shadow memory 布局要求随机化位数 ≤ 28，导致启动阶段**随机**失败
- **解决**：`sysctl -w vm.mmap_rnd_bits=28`，并写入 `/etc/sysctl.d/99-bustub-asan.conf` 持久化
- **收获**：ASan 程序"时好时坏"且无输出，先查这个内核参数，不要怀疑自己的代码

### 问题 4：gdb 下 ASan 报 `LeakSanitizer has encountered a fatal error`

- **现象**：用 gdb 调试时程序退出阶段报致命错误
- **根因**：LeakSanitizer 依赖 `ptrace`，与 gdb 冲突（提示语已明确写出 `does not work under ptrace`）
- **解决**：调试时设置 `ASAN_OPTIONS=detect_leaks=0`；测泄漏则脱离 gdb 直接运行
- **收获**：断点调试与泄漏检测是两种场景，需要不同的启动参数

### 问题 5：`make format` / `check-lint` 报 `Error 126`

- **现象**：格式化与代码检查目标执行失败
- **根因**：课程压缩包从 macOS 打包，`build_support/*.py` 丢失了可执行权限，而 Makefile 是直接调用这些脚本
- **解决**：`chmod +x build_support/*.py`

### 问题 6：`make format` / `check-lint` 报 `Error 127`

- **现象**：`/usr/bin/env: 'python3\r': No such file or directory`
- **根因**：仓库文件为 CRLF 换行，脚本 shebang 行末尾带 `\r`，解释器路径变成 `python3\r`，系统找不到
- **解决**：`sed -i 's/\r$//' build_support/*.py`
- **收获**：跨平台压缩包的两个高频陷阱——权限位丢失、换行符污染。二者在新环境首次运行质量门禁时几乎必然出现

### 问题 7：`make format` 引入大量无关 diff

- **现象**：格式化后 `git diff` 显示 13 个文件改动，包含与实验无关的测试文件
- **根因**：仓库整体为 CRLF，clang-format 顺带把其他文件也规范化为 LF
- **解决**：`git checkout <baseline> -- <无关文件>` 还原，仅保留 6 个实现文件和必要的工具脚本修正
- **收获**：批量格式化前先确认工作区干净，便于事后甄别真正的改动

## 七、调试方法总结

本次实验形成的排查顺序，可作为后续实验的参考：

### 第一层：读断言与 ASan 报告（覆盖 90% 的问题）

```
test/buffer/lru_k_replacer_test.cpp:34: Failure
Expected equality of these values:
  5
  lru_replacer.Size()
    Which is: 0
```

测试直接给出期望值与实际值。ASan 则给出出错的文件与行号。多数问题在这一层即可定位。

### 第二层：gdb 命令行

```bash
ASAN_OPTIONS=detect_leaks=0 gdb --args ./test/xxx_test --gtest_filter='*Case*'
(gdb) break 函数名
(gdb) run
(gdb) bt          # 看调用栈
(gdb) print 变量
```

配合 `--gtest_break_on_failure`，可让断言失败处直接触发断点，保留现场。

### 第三层：IDE 可视化调试

VS Code + cpptools（WSL 远程扩展）+ `launch.json`，按 F5 自动编译并进入图形化断点调试，适合观察容器内部状态。

### 辅助手段

| 手段 | 用途 |
|---|---|
| `--gtest_filter='*Case*'` | 只跑相关用例，减少噪音 |
| `--gtest_repeat=20` | 并发用例偶发失败时验证稳定性 |
| 五条不变量断言 | 缓冲池一致性问题定位 |
| 单目标编译 `make xxx_test` | 反馈周期从 26 秒降到 3 秒 |

## 八、不足与改进方向

### 8.1 LRU-K 的淘汰复杂度

当前 `Evict` 为 O(n) 线性扫描。可优化为：

- 维护两个按时间排序的链表（历史列表 / 缓存列表），配以哈希表定位节点
- 淘汰时直接取链表头，复杂度 O(1)
- 代价是需要处理节点晋升、删除、时间戳并列等边界

### 8.2 哈希表不支持收缩

题目明确说明"不需要实现收缩或压缩"，因此删除大量键后目录仍保持原大小。真实系统通常会实现合并（merge）以回收内存。

### 8.3 缓冲池的并发粒度

当前使用一把全局锁，所有页操作串行化。真实 DBMS 通常采用：

- **页级 latch**：不同页可并行访问
- **分区缓冲池**（buffer pool partitioning）：每个实例独立加锁

### 8.4 未使用页级读写锁

`Page` 对象已提供 `RLatch()` / `WLatch()`（读写锁），本次实现未使用，因为测试未要求。真实系统中，缓冲池需配合页级锁使用，以允许同一页的并发读。
