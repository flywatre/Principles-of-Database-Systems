## 1. Extendible Hash Table

### 1.1 状态与内存布局

表由**目录**与**桶**两级结构组成：

```cpp
std::vector<std::shared_ptr<Bucket>> dir_;   // 目录：2^global_depth 个槽
int      global_depth_;                      // 全局深度
int      num_buckets_;                       // 已分配桶数
size_t   bucket_size_;                       // 每桶容量（构造时传入；缓冲池中取 4）
mutable  std::mutex latch_;                  // 保护以上全部
```

每个 `Bucket` 持有 `std::list<std::pair<K,V>> list_`、容量 `size_` 与**局部深度** `depth_`。

**为什么用 `shared_ptr` 而不是裸指针**：拆分时多个目录槽会指向同一个桶，采用共享所有权后，
"哪些槽指向旧桶"可以直接用指针比较判断（`dir_[i] == bucket`），无需维护引用计数表；桶的回收交给
引用计数，不必手工 `delete`。

**为什么桶内用 `std::list` 而不是 `vector`**：删除操作只涉及迭代器失效问题，`list` 的删除是 O(1)
且不会使其他元素的迭代器失效；桶容量只有 4，遍历的常数开销可以忽略。

### 1.2 构造函数中的隐式前提

框架给出的构造函数只初始化了 `bucket_size_`，`dir_` 为空。而 `GetLocalDepthInternal(0)` 会直接
访问 `dir_[0]`，因此**构造时必须建立唯一的初始桶**（`depth_ = 0`）并放入目录。

这是一个容易被忽略的隐式前提：全局深度为 0 时目录长度应为 1，而不是 0。

### 1.3 插入与拆分策略

采用**先拆后插**（框架要求），且用循环而非单次判断：

```
while (桶已满 && 键不存在) {
    if (桶深度 == 全局深度) 目录翻倍；   // 只有一个指针指向它
    桶深度 += 1；建立新桶；
    重新分配兄弟指针；
    把旧桶的键按新深度重新分配；
}
桶内插入
```

两个关键判断：

1. **是否需要扩容目录**，取决于 `depth == global_depth`。相等意味着只有一个目录槽指向该桶，
   翻倍后才存在第二个槽；不相等说明已有多个兄弟指针，只需重新分配它们。
2. **拆一次不够**。拆分后旧桶的键可能仍全部落在同一侧（哈希低位相同），该桶依旧满载，
   因此必须回到循环开头继续拆。用 `if` 会在这种情形下静默失败（键被丢弃或插入失败）。

**重新分配的边界分析**：拆分前桶内键数恰好等于容量，拆成两个桶后任一侧的键数都不会超过容量，
因此重新分配过程中的插入不会因桶满而被拒绝。为防御性考虑，实现中仍对插入失败做了兜底，
避免在异常输入下丢失键。

### 1.4 并发

采用**单锁保护整张表**。所有公开接口进入时加锁，内部调用一律使用不加锁的 `*Internal` 版本
（`GetGlobalDepthInternal` 等）。

这一分层不是风格问题，而是**功能性要求**：`std::mutex` 不可重入，若 `Insert` 持锁后再调用
会加锁的 `GetGlobalDepth`，线程会在同一把锁上自我死锁。框架预先提供了 `*Internal` 版本，
正是为了支持这种"外壳加锁、内核无锁"的写法。

**为什么不做桶级细粒度锁**：解锁/加锁开销与锁顺序维护的复杂度，在这个规模下超过了并发收益；
而且跨桶操作（目录翻倍、兄弟指针重分配）本质上需要全表一致，细粒度锁反而容易引入死锁。

## 2. LRU-K Replacer

### 2.1 状态

```cpp
class LRUKNode {
  std::list<size_t> history_;    // 最近 k 次访问的时间戳，旧在前、新在后
  bool is_evictable_{false};     // 是否允许被淘汰
};

std::unordered_map<frame_id_t, LRUKNode> node_store_;
size_t current_timestamp_;       // 逻辑时钟，每次访问 +1
size_t curr_size_;               // 可驱逐帧的数量（= Size() 的返回值）
std::mutex latch_;
```

**为什么历史用 `std::list`**：只在尾部追加、超过 k 条时从头部删除，两端操作都是 O(1)；
`vector` 的头部删除是 O(k)，虽然 k 很小，但 `list` 的语义更贴合"定长滑动窗口"。

**为什么用逻辑时钟而不是真实时间**：比较只需要相对顺序，逻辑时钟避免了时钟回拨与精度问题，
同时使"后退 k-距离"退化为整数减法。

**为什么 `curr_size_` 需要单独维护**：`Size()` 要求 O(1) 返回"可驱逐帧数"，若每次遍历
`node_store_` 统计则与淘汰同为 O(n)。代价是所有改变可驱逐状态的地方都必须同步这个计数。

### 2.2 淘汰决策

三类候选，按优先级递减：

| 优先级 | 候选 | 判据 |
|---|---|---|
| 1 | 访问次数 < k | 后退 k-距离视为 +∞ |
| 2 | 多个 +∞ | **第一次访问**时间戳更早者 |
| 3 | 访问次数 ≥ k | 后退 k-距离更大者（= 第 k 次先前访问更早） |

实现上不排序、不建索引，单次遍历并维护一个"当前最优候选"即可，比较逻辑用三条互斥分支表达
（`is_inf` 与已选者不同 / 都是 inf / 都是有限）。

**淘汰后必须做三件事**：从 `node_store_` 删除节点、`curr_size_--`、通过出参写回帧号。
漏掉任何一件都会破坏 `Size()` 或后续的淘汰顺序。

### 2.3 复杂度与取舍

当前 `Evict` 为 **O(n)**（n = 帧数，通常等于缓冲池大小，几十到几千）。

理论上的 O(1) 方案是维护两条有序链表（历史列表、缓存列表），节点晋升时在两条链间移动，
淘汰时取链表头。**我最终没有采用**，理由：

1. 帧在两个列表间的晋升、`Remove` 的任意位置删除、时间戳并列的稳定顺序，三处边界交织，
   出错概率显著高于线性扫描；
2. 本实验中 n 的量级下，O(n) 与 O(1) 的实际耗时差异在微秒级，正确性的收益更大；
3. 题目未对复杂度提出要求，只要求算法语义正确。

这是**主动的工程取舍**，不是实现缺陷；若要面向真实负载优化，方案见第 4 节。

### 2.4 并发

单锁保护全部状态。`RecordAccess` 与 `Evict` 都会修改 `node_store_`，`SetEvictable` 会修改
`curr_size_`，三者并发即构成数据竞争，必须同一把锁。

**幂等性是易错点**：`SetEvictable(fid, true)` 在已经是 true 时**不得**再 `curr_size_++`，
否则重复 pin/unpin 会让计数漂移，`Size()` 与实际可驱逐帧数脱节。

## 3. Buffer Pool Manager

### 3.1 组件职责

| 成员 | 职责 | 由谁保护 |
|---|---|---|
| `pages_` | 帧数组，每帧含 `page_id_` / `pin_count_` / `is_dirty_` + 4 KB 数据 | `latch_` |
| `page_table_` | `page_id → frame_id` | 哈希表自身的 `latch_`，且仅在持 `latch_` 时访问 |
| `replacer_` | 淘汰候选 | 替换器自身的 `latch_`，且仅在持 `latch_` 时访问 |
| `free_list_` | 空闲帧链表 | `latch_` |
| `next_page_id_` | 页号分配 | `std::atomic`，无需 `latch_` |

### 3.2 加锁策略

**一把全局 `latch_` 保护缓冲池的全部元数据**，六个 `*Imp` 入口各自加锁

关键点是**锁的层次与顺序**：

```
BPM latch_（最外层，唯一入口）
   └─ page_table_ latch_ / replacer_ latch_（内层，仅在持外层锁时进入）
```

不存在"先拿表锁再拿 BPM 锁"的代码路径，因此**不会出现循环等待**，也就不可能死锁。
这是选择"全局单锁 + 内层独立锁"而非反向嵌套的主要理由。

**为什么锁必须加在 `*Imp` 里**：基类 `BufferPoolManager` 的 `FetchPage` / `NewPage` 等包装函数
只做回调，**不持锁**。若开发者误以为基类已加锁而省略，就会在并发用例中暴露数据竞争。

**为什么不做页级并发**：页级读写锁（`Page::RLatch` / `WLatch`）用于保护页**内容**，而缓冲池
需要保护的是**元数据的一致性**（页表与帧的对应关系、pin_count 与可驱逐状态的对应关系）。
元数据操作本身是短临界区，且跨越多个结构（页表 + 替换器 + 空闲链表），用一把锁天然原子；
拆成多把锁需要小心维持五条不变量，收益不抵风险。

### 3.3 取帧路径的抽象

`NewPgImp` 与 `FetchPgImp` 都需要"拿一个可用帧"，因此提取为私有函数 `AcquireFrame`：

```
空闲链表非空 → 直接取
否则 → 让 replacer 选牺牲帧
        全部被 pin → 失败（上层返回 nullptr）
        否则：脏页写回 → 从页表移除 → 重置帧
```

**提取的理由**：这条路径包含"空闲优先、按需驱逐、驱逐前写回"三个决策，若两个调用点各写一遍，
极易出现其中一个漏写 `WritePage` 或漏改 `is_dirty_` 的情况；集中一处可保证行为一致。

### 3.4 一致性不变量

实现中始终维持以下不变量，它们同时也是调试时的断言依据：

1. `page_table_` 中有某页 ⟺ 存在帧满足 `frame.page_id_ == 该页号`
2. `pin_count_ > 0` 的帧，在 replacer 中必须**不可驱逐**
3. `pin_count_ == 0` 的帧，在 replacer 中必须**可驱逐**
4. `free_list_` 中的帧 `page_id_ == INVALID_PAGE_ID`，且不在页表与 replacer 中
5. 任一 `page_id` 至多对应一个帧

不变量 2、3 是最容易破坏的：`FetchPgImp` 命中时若只 `pin_count_++` 而忘记
`SetEvictable(false)`，该页就可能在仍被使用时被驱逐；`UnpinPgImp` 若在 `pin_count_` 未归零时
就置为可驱逐，同样会破坏一致性。

### 3.5 边界行为

| 情形 | 约定 |
|---|---|
| 池满且全部帧被 pin | 返回 `nullptr`，不修改出参 |
| `Unpin` 一个 `pin_count_ == 0` 的页 | 返回 `false`，不减成负数 |
| `Delete` 一个被 pin 的页 | 返回 `false` |
| `Delete` 一个不在池中的页 | 返回 `true`（视为已删除） |
| `Flush` 一个不在池中的页 | 返回 `false` |
| 驱逐脏页 | 必须先 `WritePage` 再复用帧 |

## 4. 权衡与未采用的方案

### 4.1 考虑过但放弃的做法

| 方案 | 放弃原因 |
|---|---|
| 哈希表用桶级细粒度锁 | 目录翻倍与兄弟指针重分配需要全表一致；加锁顺序复杂，易死锁 |
| LRU-K 用双有序链表实现 O(1) 淘汰 | 晋升、任意删除、时间戳并列三处边界交织，正确性风险高于收益 |
| 缓冲池用页级分段锁 | 元数据跨三个结构，拆分后难以维持第 3.4 节的五条不变量 |
| 拆分时用"插满再拆"（分裂后检测） | 违反题目要求，且桶会短暂超过容量，`GetNumBuckets` 语义受影响 |
| 用 `vector` 存放桶内键值对 | 删除会移动元素，多次删除下迭代器管理更易出错 |

### 4.2 若面向真实负载的改进方向

1. **LRU-K 的 O(1) 淘汰**：双链表 + 哈希表定位，节点晋升时在两条链表间移动；
   需为"历史不足 k 次"和"已满 k 次"分别维护顺序。
2. **哈希表收缩**：删除后检测兄弟桶是否可合并，合并即局部深度减一，可回收目录与桶内存
   （本实验题目明确不要求）。
3. **缓冲池分区**：按 `page_id` 哈希到多个独立实例，每个实例自带锁与替换器，
   在保持局部一致性的前提下提高并发度。
4. **页级读写锁**：与缓冲池元数据锁分离，允许同一页的并发读、不同页的并行访问。
